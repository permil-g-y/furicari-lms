運営スタッフが SQL を
卒業するための管理画面

Phase 7 の目的は、高機能な管理システムを作ることではありません。 非エンジニアの運営スタッフが Supabase と Cloudflare を一度も開かずに、 フリキャリの日常業務を回せる状態にすることです。

2026-08-21対象コミット b223474（Phase 6 完了）設計のみ / 実装未着手

01優先度を決めた基準

「あると便利か」ではなく「何回起きるか」で切る

機能の要不要は、運営でその作業が何回発生するかだけで判断しました。 毎週起きることは画面へ移し、数ヶ月に一度のことは SQL のままで構いません。 画面を作るコストは、そこで節約できる手作業の回数に見合ったときだけ正当化されます。

週に一度起きることは、画面にある。
数ヶ月に一度のことは、SQL でよい。

この一行が、以下すべての優先度判断の根拠になっています。

02前提 — DB 側はもう準備できている

Phase 7 は「作り直す仕事」ではなく「画面を載せる仕事」

Phase 1 の設計時点で、全テーブルに管理者用の RLS ポリシーが既に入っています。 is_admin() も、profiles.role の権限昇格防止（列レベル権限 + トリガの二層）も実装済みです。 

public.courses / chapters / lessons / categories / tools   Admins manage …
public.user_course_enrollments                             Admins manage …
public.announcements                                       Admins manage …

そのため Phase 7 で必要な DB 変更は最小限に収まります（→ 06）。 新しい権限体系を作るのではなく、既にある権限の上に画面を載せるだけです。

04管理者権限とアクセス制御

画面を隠すことをセキュリティにしない

ログインは受講生と同じ /login を使います。管理者専用のログイン画面は作りません。 入口が 2 つあると、片方の穴が全体の穴になるためです。

層何をするか役割
1proxy.ts で /admin を早期に判定するコスト削減
2(admin)/layout.tsx で requireAdmin()UX
3RLS が admin 以外の読み書きを拒否する本丸

Secret Key を使う場所を 1 箇所に固定する

管理操作は原則すべて、ログイン中の admin ユーザーの権限（RLS）を通して行います。 RLS を貫通する Secret Key を使うのは、受講生の招待 1 経路だけです。 auth.admin.inviteUserByEmail() が Admin API でしか呼べないためで、 呼ぶ直前に必ず requireAdmin() を通します。 これで「強い鍵が使われる場所」がコード上 1 箇所に固定され、レビューできる状態になります。

意図的に画面へ置かないもの

管理者を増やす操作（profiles.role の変更）は、管理画面に置きません。 置いてしまうと、管理画面の脆弱性 1 つがそのまま権限昇格につながります。

管理者の追加は実質「ほぼ起きない」頻度なので、SQL での手動運用を維持します。 これは手抜きではなく、構造的に事故を不可能にするための設計判断です。

05Cloudflare 連携 — 動画を Vercel に通さない

Direct Creator Upload を使い、UID の照合処理そのものを無くす

1. 管理画面 ──────▶ Route Handler
2. サーバー ──────▶ Cloudflare  POST /stream/direct_upload
                     { requireSignedURLs: true, meta: { lessonSlug } }
3. Cloudflare ────▶ uploadURL と uid が返る
4. サーバー ──────▶ その場で lessons.stream_video_id = uid ← 紐付け完了
5. ブラウザ ──────▶ uploadURL へ直接 PUT（動画は Vercel を通らない）
この方式を選ぶ理由内容
サイズ制限Vercel の関数にはリクエストボディ上限がある。数百 MB の動画は通せない
UID が発行時に確定する「アップロード後に UID を探して貼る」照合処理が丸ごと不要になる
署名必須を維持できるrequireSignedURLs: true を指定でき、Phase 4 の前提を崩さない

中断への備えと、動画尺の自動反映

アップロードが中断されると「UID はあるが動画が無い」状態が残ります。 これを lessons.stream_status（pending / ready / error）で表現し、 ready でないレッスンは公開できないようにします。

動画尺は Cloudflare が返す duration をそのまま使います。取得は 3 段構えです。

方式優先度内容
アップロード後のポーリング必須変換完了まで数十秒〜数分。画面に「処理中」を出す
手動の「情報を取得」必須ポーリングが途切れても必ず復旧できる逃げ道
Webhookできれば署名検証が必要。上 2 つで足りる
既存 90 件の不一致について

管理画面に「全レッスンの動画情報を一括再取得」を置きます。Phase 6 で先送りした duration_seconds の不一致は、これ 1 回で解消します。

ただし一度「完了」になった進捗は絶対に取り消しません。 尺が伸びた結果として完了が未完了に戻るのは、受講生にとって理不尽だからです。 一括更新では status に触れません。

06DB 変更

既存の受講生向けポリシーは 1 つも変更しない

#変更理由
1lessons.stream_status 追加アップロード中断を表現する
2lessons.stream_synced_at 追加いつ Cloudflare と同期したか
3lesson_progress に admin の SELECT を追加現在は本人しか読めず、admin が進捗を見られない
4lesson_view_events に同上学習状況の集計に必要
5admin_user_overview viewメールと最終ログインを admin にだけ見せる

3 と 4 は「RLS を緩める」変更ではありません。 既存の本人ポリシーはそのまま残し、is_admin() を条件とする別のポリシーを追加します。 受講生から見える範囲は一切変わりません。

5 の view は security_invoker と is_admin() で二重にガードします。 profiles にメールアドレスを複製する案は採りません。二重管理になり、必ず食い違うためです。

07実装順

最頻業務をできるだけ早く SQL から降ろす

  1. 管理画面の土台7-ARoute Group / requireAdmin() / proxy の早期拒否 / 空のダッシュボード。admin だけが /admin に入れる状態にする
  2. 受講生一覧・詳細（読み取りのみ）7-Badmin 用の RLS ポリシーと view を追加。誰がどのコースを受講しているかが画面で分かる
  3. 受講権限の付与・解除・期限7-C最頻業務がここで SQL を卒業する。ここを早く置くために 7-B は読み取りだけに絞ってある
  4. 受講生の招待7-DSecret Key 経路。招待から視聴開始まで画面で完結する（※ SMTP の判断が必要）
  5. アップロードと自動紐付け7-ECloudflare アップロード / UID 自動紐付け / 尺の自動取得。動画追加が画面で完結する
  6. 既存 90 件の尺を一括再取得7-F7-E の副産物。Phase 6 で先送りした不一致が解消する
  7. お知らせの作成・編集・公開7-G本文は既存の jsonb ブロック配列のまま。リッチエディタは作らない
  8. レッスン編集とダッシュボード仕上げ7-H編集・並び替え・公開切替。「⚠ 要対応」が機能する状態にする

08Custom SMTP をどうするか

結論：Phase 7 に含めるべき。というより前提条件

Supabase の共有 SMTP は開発用で、送信レート制限が厳しく、本番の招待には耐えません。 招待メールが届かない = 受講生が入れない = サービスが始まらないため、 これは「あると良い機能」ではなく前提条件です。 差出人ドメインの都合で迷惑メール判定されやすい点、メール文面を日本語にできない点も同じ理由です。

候補特徴
Resend設定が最も簡単。Supabase の公式ドキュメントでも例示されている
SendGrid実績が長く、到達率のレポートが厚い
Amazon SES最安。ただしサンドボックス解除の審査に時間がかかる

なお、外部サービスへの新規契約は私の判断では行いません。 判断が必要なのは「どれを契約するか」だけで、実装側の作業はどれを選んでも同じです。

11Phase 7 完了時にできる状態

運営スタッフが Supabase / Cloudflare を開かずにできること

  • 新しい受講生を招待し、その場で受講コースと期限を設定する
  • 「見られません」の問い合わせを 1 画面で調査し、その場で直す
  • 受講期限を延長・停止し、期限切れ間近を事前に把握する
  • 新しい動画をアップロードして公開まで完結する（UID も尺も自動）
  • お知らせを書き、公開日を決めて出す（予約公開も可）
  • 誰がどこまで進んでいるか、どのレッスンで脱落しているかを見る
  • 「⚠ 要対応」で、動画未設定・期限切れ間近・未ログインの招待に気づく

SQL が残るのは「新しいコースを立ち上げる」「カテゴリを増やす」「管理者を増やす」の 3 つだけです。 いずれも数ヶ月に一度以下の頻度で、最後の 1 つは安全のために意図的に残しています。
